**Key web-verified insight from [Infralovers 2026-07-14](https://www.infralovers.com/blog/2026-07-14-local-model-ai-coding-tools-benchmark/):** "Friction and autonomy don't move together." The leanest harnesses (OpenCode, Pi) need the most hand-holding on local models. The most structured (Claude Code) produces the most autonomous results but takes ~40 minutes vs ~10-15 for others on the same task. **This is directly relevant to llm-tune's recommendations** — the tuning advice should differ based on which harness the user is in.

### 1b. MCP bloat: the silent killer for local models (verified)

- **[Atlassian mcp-compressor](https://www.atlassian.com/blog/development/mcp-compression-preventing-tool-bloat-in-ai-agents)**: 70-97% token reduction on MCP tool descriptions. A GitHub MCP server's 94 tools = **17,600 tokens** uncompressed → **500 tokens** at max compression. Four levels: `full` (17,600) → `brief` (3,900) → `minimal` (3,300) → `none` (500, requires `list_tools()` discovery).
- **[Dev.to: MCP bloat hits local models harder](https://dev.to/shenao_yu_e15c14815264a44/mcp-tool-bloat-hits-local-models-harder-a-constraint-worth-talking-about-oon)**: "A cloud-hosted model with 128k context can absorb verbose tool descriptions from three or four MCP servers and still have room for the task. A local model with an 8-32GB VRAM context window has no such luxury."
- **Key takeaway for llm-tune**: The skill should include a **Harness Debloat** function — explicit guidance on stripping MCP servers, reducing tool schemas, and choosing local-only toolsets when running on consumer hardware. This is not optional advice for 8-16GB users; it's survival advice.

**File**: `skill/references/tables/hardware-tiers.md` (new)
**Content**: For each tier (8GB, 12GB, 16GB, 24GB, 32GB, 48GB, 64GB+, cluster), what quant/model fits, what context is affordable, what the failure modes look like, and what the bench should be.

**Format**: Same as existing tables — measurements, sources, findings.
**Key measurements to include per tier**:

- Decode t/s range (labeled as estimate for tiers not in the lab)
- Context ceiling before OOM
- MTP fit impact (flat +0.42 GiB transfers; draft context OOM risk scales with VRAM scarcity)
- Recommended `-ub` setting per tier (ub1024 gains architecture-dependent, not VRAM-class dependent)

#### 2.2. Harness-Specific Tuning Section

**File**: `skill/references/harnesses.md` (new) or integrated into `SKILL.md` Step 8 expansion
**Content**: Tuning advice that changes based on which harness the user is in.
**Data source**: Infralovers benchmark (same model, 4 harnesses, 64GB M1 Max, Qwen3.6-35B-A3B), user's lab data (Pi, OMP, Claude-local, OpenCode).
**Key insights to encode**:
- **Pi/OMP**: Leanest tool surfaces (compact ~28k tokens). Tuning priority: tool-call reliability > context size > speed. These harnesses reject malformed calls hard (Pi rejected all `write` calls without `path`). Recommend: keep models small enough that tool-call accuracy matters most.
- **Claude-local**: Reduced tool set, strict validation. Tuning priority: quality > context > speed. These harnesses have fewer tools to bloat.
- **OpenCode**: Blend of local+cloud, full skill set. Tuning priority: balanced — this is where context bloat from cloud habits hits local models hardest. Recommend: explicit debloat for local-only sessions.
- **Claude Code**: Plan+sub-agents, most autonomous but slowest (~40 min vs ~15 for others on local models). Tuning priority: context size + quality > speed. These harnesses burn more context on planning, so larger ctx windows are more valuable.
- **Claude Code local mode**: Point at local endpoint via env vars (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_DEFAULT_SONNET_MODEL`). Same autonomy, no cloud dependency.

#### 2.3. Context Size Decision Tree

**File**: New section in `SKILL.md` Step 2, or `skill/references/context-decision.md` (new)
**Content**: A decision tree: "Given my hardware tier, workload type, and harness, what context size should I target?"
**Data source**: Existing tables (kv-cache.md T1-T3, context-recall.md T1-T7, prefill-decode-speed.md T5-T8).
**Decision factors**:
1. Hardware VRAM tier → max affordable KV at q8_0
2. Workload type → minimum depth needed (chat=shallow, agent=medium, research=deep)
3. Harness context budget → some harnesses cap declared context (Copilot at 32k needed manual bump)
4. Declared ctx vs usable ctx → always verify recall at depth (finding 7)

#### 2.4. Harness Debloat Function

**File**: New section in `SKILL.md` (after Step 8), or `skill/references/debloat.md` (new)
**Content**: Explicit guidance for users running local models on limited VRAM — how to strip MCP servers, reduce tool schemas, and choose local-only toolsets.
**Data source**: Atlassian mcp-compressor (70-97% reduction), Dev.to article on local-model bloat, user's Pi/OMP/Claude-local reduced-tool configs.
**Key content**:
- **The rule**: On 8-16GB VRAM, every MCP tool description that loads costs context you cannot afford. Cloud models with 128k+ context absorb this; local models cannot.
- **The hierarchy** (what to keep, what to strip):
  - Keep: tools the agent calls directly in its core workflow (grep, file-read, write, shell)
  - Strip: tools the agent calls <5% of the time (Jira, Confluence, GitHub issues)
  - Strip: tools the agent calls via other tools (MCP-in-MCP chains)
- **Compression options** (from Atlassian data, transferable):
  - `full` → `brief`: 78% reduction (17,600 → 3,900 tokens for GitHub MCP)
  - `full` → `minimal`: 81% reduction (17,600 → 3,300)
  - `full` → `none`: 97% reduction (17,600 → 500, but requires `list_tools()` discovery)
- **Local-only harness recommendation**: When VRAM < 16GB, run a dedicated local harness with only 5-7 tools (like the user's Pi/OMP/Claude-local setup). Don't load cloud-skills into a local model.
- **mcp-compressor reference**: `pip install mcp-compressor`, wraps existing MCP server, no client changes needed.

#### 2.5. Safety Command: "Validate with Operator"

**File**: New section in `SKILL.md` Traps or Rules, or dedicated `skill/references/safety.md` (new)
**Content**: An explicit safety protocol for destructive operations.
**Data source**: AGENTS.md hard limits (Kali VM 250 off-limits, never touch, ask before irreversible), user's request for explicit safety commands.
**The function**:
```
## Safety: Validate with operator

Before executing any of the following, the agent MUST:
1. State exactly what it will do (files, models, paths, commands)
2. Ask "validate with operator" — wait for explicit approval
3. Not proceed until the operator confirms

Destructive operations requiring validation:
- Deleting model files or quant variants
- Removing model directories or HF downloads
- Deleting KV cache or draft context files
- Rotating credentials or API keys
- Exposing a service publicly (beyond the one public service: jellyfin.ttindall.com)
- Destroying or resetting any VM/container
- Force-pushing or rewriting git history
- Modifying production config without backup
```
**The phrase**: When the agent encounters a request for removal or deletion of quants/files/models, it should respond:
> "This involves deleting [specific thing]. I need to validate with operator before proceeding. Here's exactly what will be removed: [list]. Confirm and I'll proceed."

### Tier 2: User Journey & Model Management (ship shortly after public)

#### 2.6. User Journey Branching

**File**: `skill/references/user-journeys.md` (new) or restructure `SKILL.md` Section 1 (Intake) to branch
**Content**: Four entry states, each with a distinct workflow.

**State A — "I have no models, I'm just getting started"**
1. **Install HF CLI**: `pip install huggingface_hub` → `hf download` for model pulls
2. **Choose your hardware tier** (link to hardware-tier table)
3. **Pick the simplest entry quant** for your tier:
   - 8GB: 7-8B Q4_K_M (or a 3.8B model if VRAM is tight)
   - 16GB: 13-17B Q4_K_M
   - 24GB: 27B Q4_K_M (or 30B A3B MoE at Q4)
4. **Install a simple serving engine**: Ollama (easiest) or llama.cpp (most tunable)
5. **Run the bench**: `bench/quick_bench.md` — memory accounting first
6. **Start with a simple workload**: chat or single-turn task
7. **Graduate to agent workload** once chat works reliably
8. **Add harnesses incrementally**: start with OpenCode (blend), move to Pi/OMP/Claude-local when you need local-only

**State B — "I have models and they are here"**
1. **Inventory your models**: file size, quant, whether they carry MTP tensors, registered context
2. **Run the fit check**: For each model, read engine memory log → `KV buffer size`, `compute buffer size`, peak VRAM per run
3. **Run recall at depth**: `bench/needle.py` at 10/50/90% — declared ctx ≠ usable ctx
4. **Run the quality probe**: `bench/quality_probe.py` with repeats
5. **Identify the binding constraint**: Is it VRAM (→ Step 1 of SKILL.md), context (→ Step 2), speed (→ Step 4/5), or quality (→ Step 6/7)?
6. **Tune per the decision procedure**: Each step's verify section tells you what to check
7. **Contribute your data**: Use `CONTRIBUTING.md` template — your numbers become the next version of the skill

**State C — "I have 64k+ context but my agents are barely usable"**
1. **Diagnose the real bottleneck**: Is it context size, or is it tool-call reliability, or is it harness bloat?
   - Check: does the agent complete a 64k-context task end-to-end? (If not → tool-call or harness issue, not context)
   - Check: does the agent complete a 32k-context task with tools? (If not → tool-call reliability issue)
2. **Check harness context overhead**: Some harnesses spend 60% of context on tool definitions before seeing the task (Copilot at 32k). Reduce MCP load first.
3. **Apply Harness Debloat** (Section 2.4): Strip MCP servers, compress tool schemas
4. **Switch to a local-dedicated harness**: Pi, OMP, or Claude-local with reduced tool set
5. **Tune for the harness**: Different harnesses need different settings (Section 2.2)
6. **Verify improvement**: Run the same task set before/after, quality metric held constant

**State D — "I'm advanced, I want to squeeze every bit"**
1. **Engine A/B**: Try NInfer vs Strata vs llama.cpp on the same model, same harness (r12 methodology)
2. **KV quant A/B**: q4_0 vs int8 KV with recall held constant (r13 methodology)
3. **Speculative depth sweep**: d2/d3/d4/d5 per workload, 3 runs each (ninfer-sweep1 methodology)
4. **Prefill chunk A/B**: alternating arms, depth-held, quality-constant (strata-ctx methodology)
5. **Engine version A/B**: PR #646 methodology, alternating arms
6. **Contribute to the tier tables**: Your advanced data fills the gaps for other hardware tiers

#### 2.7. Model Management & HF Download Integration

**File**: New section in `SKILL.md` or `skill/references/model-management.md` (new)
**Content**: How to acquire, organize, and safely remove models.

**Download workflow**:
```bash
# 1. Install HF CLI
pip install huggingface_hub

# 2. List available quants
hf api huggingface.co/api/models?author=mlx-community&search=Qwen3-Coder&limit=50

# 3. Download a specific quant (safetensors)
hf download mlx-community/Qwen3-Coder-30B-A3B-Instruct-4bit \
  --local-dir ./models/Qwen3-Coder-30B-A3B-4bit

# 4. For GGUF (llama.cpp), find the model on HF and download the .gguf file
hf download <org>/<model> --include "*.gguf" --local-dir ./models/

# 5. Verify the download (check file size matches expected)
ls -lh ./models/<model>/
# Compare against the table in skill/references/tables/vram-fit.md
```

**Model inventory template** (contribute to `data/INVENTORY.md`):
```
- Model: <name>
- Path: ./models/<path>
- File size: <GiB>
- Quant: <Q4_K_M / IQ4_XS / etc.>
- MTP tensors: yes/no
- Registered ctx: <n>
- Peak VRAM at ctx: <MiB>
- Engine: llama.cpp / Strata / NInfer / MLX
- Status: working / OOM / partial / untested
```

**Safety — removal/deletion protocol**:
> **DELETION REQUIRES VALIDATE-WITH-OPERATOR**
> Before deleting any model file, quant variant, or HF download:
> 1. Confirm: this model is not your only instance (do you have a backup? Is it on another machine?)
> 2. Confirm: you know the exact path and what will be removed
> 3. State: what you lose (the quant, the file, the data) and what you keep
> 4. Wait for explicit operator approval
> 5. Use `rm -ri` (interactive) for file deletion, never `rm -rf` for model files
> 6. After deletion: update your model inventory

#### 2.9. Multi-Node / Cluster Guidance

**Content**: For users with 5x DGX Spark or 3x RTX 6000 — brief reference to vLLM multi-node (tensor parallel across GB10/RTX 6000 nodes), NVIDIA Sync for cluster management, and the key insight: **cluster tuning is about load balancing and KV distribution, not per-node tuning.** llm-tune's per-node advice still applies; the cluster adds a resource-orchestration layer.
**Sources**: NVIDIA developer forums (multi-node vLLM on DGX Spark), MindStudio (clustering DGX Sparks over RDMA), vLLM blog (DGX Spark architecture).

#### 2.10. Context Recall as a First-Class Metric

**Content**: Elevate "recall at depth" from a bench step to a core metric alongside tok/s and quality score. The existing data shows:
- Declared context is NOT usable context (Quality-131K scored 0/3 at 120k with HTTP 400)
- Recall holds at depth when memory allows (every entry that loaded in r9 scored 6/6 or 9/9)
- The binding constraint is memory, not attention quality (r9 finding)
**Implication**: The skill should always recommend recall-at-depth testing before declaring a context size "good."

#### 2.11. Quality-Per-Second as Role Selection Metric

**Content**: Already in findings (finding 30, corrected). Strengthen with the Infralovers data: Claude Code (most structured) was slowest but most autonomous; Pi (leanest) was fastest but needed most hand-holding. **The metric for role choice is not just quality — it's quality per second of agent runtime, including the harness overhead.**
